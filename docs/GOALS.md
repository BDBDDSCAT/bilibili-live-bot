# 项目改进目标

更新时间：2026-10-07。目标按实际代码和现有问题推进，每轮完成后记录验收结果。

## 第一轮：正确识别初始化期间下播的房间

状态：已实现，待合并。

房间初始化依次请求 `room_init` 和 `getRoomBaseInfo`。两次请求期间主播可能下播；原实现把后一个接口的 `live_status: 0` 当作缺失值，保留旧的直播状态。控制台和运行时的直播状态门禁因此可能收到过期信息。

- 后一个接口返回明确的 `0`、`1` 或 `2` 时采用该状态；缺失或为 `null` 时保留初始化结果。
- 初始化期间下播时，客户端发出的房间事件显示“未开播”。
- 加入离线合成接口测试，覆盖下播、开播、轮播、缺失状态和可选接口失败，不访问真实房间或执行发送。
- 验收：`node --test scripts/test-bilibili-client.js` 和 `npm run check` 全部通过；测试前旧实现应稳定复现三个失败用例。

验收结果：旧实现出现三个预期失败；修复后新增测试 9/9 通过。Node.js 20.20.2 和 24.19.0 的 `npm run check` 通过（120 个单元测试、55 个回归检查及公开发布门禁）；Node.js 22.23.3 的 120 个单元测试通过。`npm audit --omit=dev --audit-level=high` 未发现漏洞。

## 第二轮：停止或重启后隔离过期监听请求

状态：已实现，待合并。

停止后再次启动会将 `stopped` 改回 `false`，原先尚未完成的房间查询或 token 刷新因此仍能写回，并再次创建连接。此外，替换 WebSocket 时旧连接的迟到关闭事件会被忽略，原先的心跳定时器却没有随替换清理。

- 每次启动取得独立代次；停止或再次启动后，旧查询、旧错误和旧重连不能影响当前房间或连接。
- 房间信息和弹幕配置准备完成后一起写回，客户端只发布当前启动的房间事件。
- 替换连接前清理心跳和重连定时器；事件回调中触发停止时，随后不得继续创建连接或心跳。
- 关闭事件回调中的停止或重启优先于原操作；旧关闭事件不得为新启动提前安排重连。
- 停止时立即取消心跳和重连；正常关闭会清理关闭保护定时器，不响应关闭握手的连接仍由三秒保护强制终止。
- 验收使用合成 API、模拟 WebSocket 和可计数定时器，覆盖请求迟到、失败、连接替换及关闭顺序，不连接真实直播间。

验收结果：新增 17 个生命周期测试，旧实现稳定复现 14 个失败；修复后监听器测试 26/26 通过。Node.js 24.19.0 的 `npm run check` 通过（137 个单元测试、55 个回归检查及公开发布门禁）；Node.js 20.20.2 和 22.23.3 的 137 个单元测试均通过。依赖审计未发现漏洞。
